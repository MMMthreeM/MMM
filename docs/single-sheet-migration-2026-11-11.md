# 單一 Google Sheets 架構與資料搬移｜2026-11-11

## 結果

依使用者本輪明確選擇，應用程式改用單一 Google Sheets 業務資料來源；保留既有登入／Company 權限、Redis 全域寫入鎖、Origin／JSON／容量檢查、限流與稽核。PostgreSQL Authority、獨立最新 Head、受管理空白 Genesis 與舊 H2 儲存契約不再是目前路由的執行前提。

這是新的明確儲存契約，不是假裝通過舊版的獨立回滾證明。Google Sheets 與其編輯者是業務資料信任來源；人工改表或整體還原須依 Drive 版本、稽核與受控維運程序處理，沒有承諾抵抗所有資料及稽核被一起還原的情況。

已將舊庫的 62 張需求、356 筆材料寫入使用者指定的新庫並逐格讀回核對。59 張已送達、3 張審核完畢（16 筆材料），狀態未改。Users 3 筆、Materials 182 筆、Audit_Logs 13 筆、公告 1 筆原本即與來源相同，未重複追加。舊庫的內容與權限皆未修改。

## 固定資料契約（Schema_Version = 3）

仍使用七張表，業務表不提供 v1/v2 自動相容或缺欄補救：

- **Orders：21 欄**，沿用現有欄名／順序。Schema_Version 為數值 3，Namespace_ID 固定 `single-sheet`；Line_ID 是新分配且之後不隨數量／備註修改的永久 UUID。日期轉成明確的本地民用日期時間字串，數量仍為真正數值。
- **Draft_Item_State：13 欄**，保留既有表頭，Schema_Version 為 3。每筆材料一列，保存原始七欄內容、目前內容指紋與確認狀態；與 Orders 一對一核對。沒有把空白舊資料推定成確認完成。
- **Order_History：10 欄**：Schema_Version、Event_ID、Order_ID、Event_At、Actor、Event_Type、Part_Index、Part_Count、Payload_Digest、Payload_Part。較長 JSON 分成安全的小段、校驗完整性後才還原。搬移紀錄為 DATABASE_IMPORTED，保留來源欄名及每列原值，不捏造過去審核或出貨事件。
- **Users／Materials／System_Notices／Audit_Logs** 延用既有具名表頭及權限／價格隔離規則。讀寫只使用指定的新庫。

Orders 的 Created_Event_Ref 保留為儲存欄位，其固定識別文字不是舊 H2 見證。2026-11-12 已移除 PostgreSQL 模組與舊庫相容路徑；嚴格解析與指紋工具保留，Schema 3 讀取失敗不回退舊庫。

## 搬移方式與資料保留

1. 兩份 Sheet 中繼資料及原始型別唯讀盤點；確認新庫業務區無案件，四張輔助表內容相同。
2. 離線轉換／讀回驗證，保留原單號、申請者、工班、材料、數量、單位、廠商、備註、審核者與狀態；同名分筆不合併。
3. 舊 Sheet 日期序號依 1899-12-30 民用日期基準轉換，不以 UTC 時差挪動日期。發現一張歷史單各列有兩個不同日期，逐列保留，未強制統一。
4. 保存私有的來源盤點及固定 ID 轉換結果於 Git 已忽略的 `.tools/database-migration-2026-11-11/`。轉換工具拒絕覆蓋已存在的 manifest，避免重跑重新分配 ID。
5. 寫入前重新讀取來源 Orders／Materials 與新庫三張業務表，確認來源未變、新庫仍為空。以同一次原子 batch 寫入 21／13／10 三表，清除 History 舊版多餘的表頭文字。
6. 新庫逐格原始型別讀回與預備資料完全相同：Orders 357 列、Draft_Item_State 357 列、Order_History 63 列，皆含表頭。
7. 新庫名稱改為「MMM｜新版材料需求資料庫（單一 Sheets）」；經使用者明確批准，將舊庫原有程式服務帳號的 writer 權限延續至新庫，再以程式真實服務帳號成功讀回全部需求。

Drive 額外備份副本最初被自動審查拒絕（目的地未驗證），未建立該副本、沒有改道複製。服務帳號授權也曾要求特定帳號的明確同意；使用者批准後才成功執行。原庫維持原狀，可供核對；不要把原庫與新庫同時當作日後新需求的寫入來源。

## 寫入、回應不明及權限

業務寫入仍由 secureMutation 授權、限流、保存稽核意圖並取得全域鎖；在鎖內讀取完整新庫、核對角色／Company／狀態、材料來源與數量規則、整單或涉及列的內容指紋，再執行單次 Sheets batch。送出前再次確認快照、材料庫與鎖擁有者；送出後重讀比對，才回 confirmed。沒有用 HTTP 200 代替資料核對。

正式材料確認使用與使用者／需求／內容／操作綁定且短效的簽章，金鑰取 SHEETS_CONFIRMATION_SECRET，或足夠長度的 NEXTAUTH_SECRET。本機已配置專用隨機簽章金鑰，未輸出或提交值。草稿可暫存數量業務規則待處理項，但正式送出仍完整驗證。

ACK 遺失或寫後核對失敗時保留鎖、回 unknown／acknowledged-unverified、不自動重送。作業查詢只讀 History 中同批寫入的回執，保留 Company 隔離，不自動解鎖或發新作業。人工解除待核實鎖前，仍須核對真實結果。

## 部署與操作交接

本機 GOOGLE_SHEET_ID 已切換至新庫；其他憑證未輸出。正式網站尚未切換，須部署這份新程式並於主機設定新 GOOGLE_SHEET_ID、SHEETS_CONFIRMATION_SECRET（至少 32 bytes，透過安全設定流程產生）、既有登入／Google／Redis／通知設定，然後執行角色與狀態操作驗收。舊 PostgreSQL、MMM_V2_*、Genesis 與獨立 Head 設定不再是目前路由的啟用條件。

若要退回舊網站，必須讓舊程式指向未改動的舊庫；不能把舊程式接到 Schema 3 新庫。新庫已有後續合法寫入時，也不能以搬移前空表覆蓋。回復應先停止寫入、保存最新資料並核對差異。
