## 明確問題與修正順序

### F00｜P1：品牌基礎仍在，表單構圖與操作節奏已明顯改變

- 舊版 `app/globals.css` 的 484 行保留，目前另外追加 177 行 v2／T09 規則。主色、字型及基本按鈕沒有全面更換；改變感主要來自容器、資訊層級與工具密度。
- 舊版 `components/OrderForm.tsx` 用兩步進度、選料白色工作面／摘要側欄、白色確認卡片。載入既有單先進確認卡片。現版 `V2OrderEditor` 將整個材料編輯器直接放在畫布上，增加清單搜尋、問題篩選、合併／撤銷、逐筆來源確認、原資料與歷史入口。材料列之間主要靠分隔線區分。
- 舊版管理員使用專用材料／廠商對應表單，主要欄位直接呈現；現版改嵌同一個共用編輯器，管理員也看到新增材料、文字叫料、全清單工具及逐筆確認，且廠商改藏於逐筆 details。
- 因此視覺改變有來源依據。共用編輯、就地數量及智慧備註符合 PDF 的功能方向，但大量反覆工具與不同的工作面構圖不是完成這些功能的必要條件。
- 修正方向：以 GitHub 這版的白色工作面、字級／間距層級及清楚的主要動作作視覺基準，將已選定的新流程整合進來；針對工班與管理員分別配置常用工具。後端資料契約與安全驗證維持獨立檢查。

### F01｜P1：文字叫料重複逐筆確認

- 規格：階段 9，PDF 第 43 頁；解析階段人工確認後仍保留整單最後確認，避免在多個階段重複確認相同內容。
- 實作：`components/TextOrderImport.tsx:59` 在加入前要求每筆 `confirmed`；`components/TextOrderImport.tsx:61` 輸出已確認材料，但 `components/OrderForm.tsx:145` 建立清單列時一律設 `confirmed:false`。`components/OrderMaterialLine.tsx:18` 與 `components/OrderForm.tsx:156` 再次阻擋最後確認。
- 影響：批次 100 筆已逐筆確認，加入清單後仍須再勾 100 次；畫面「每筆只需確認一次」與實際行為衝突。
- 修正：在相同內容與來源下傳遞前端人工核對狀態；任一相關內容變更才使確認失效。伺服器的受控確認與正式完整驗證仍須保留，不能把前端 checkbox 當作可信寫入證據。

### F02｜P1：一般修改後沒有回到桌機原工作脈絡

- 規格：階段 11，PDF 第 51–53 頁與第 150 頁；既有待審核修改回原詳情並提供短成功提示，桌機保持列表與詳情並列。
- 實作：`components/OrderForm.tsx:130` 的 `amend-order` 固定導向 `detailHref()`；只有前一行 `resubmit-order` 有桌機寬度分流。`components/CrewOrders.tsx:33` 的獨立詳情頁只顯示重新送出成功提示，沒有一般修改成功提示。
- 影響：從桌機側詳情修改，儲存後離開左右分割畫面；使用者須重新找回列表，且無法立即確認更新完成。
- 修正：一般修改也依裝置回原單、保留列表條件／頁碼／焦點；收到 confirmed 後顯示一次成功提示。窄畫面繼續使用獨立詳情。

### F03｜P1：畫面容許完整填單，實際寫入能力卻尚未就緒

- 本機 `.env.local` 的 `GOOGLE_SHEET_ID` 與使用者提供的 Sheet 不同。僅在記憶體比較是否相等，未輸出另一份 ID 或任何憑證。這是本機檔案設定證據，不能推定遠端部署的設定。
- 本機檔案缺少 v2 Writer 啟用與數項 Authority 設定。更重要的是，`lib/order-authority.server.ts:76` 的真實 `PostgresOrderAuthority.head()` 會在相依服務尚未實作時固定拒絕，回報 `INDEPENDENT_HEAD_PROVIDER_NOT_CONFIGURED`。因此僅補環境變數也不能完成真實流程。
- 寫入門檻見 `lib/order-actions.ts:25`；正式確認門檻見 `app/api/orders/confirmation/route.ts:45`。`components/OrderForm.tsx:30` 的全新填單只讀材料，不查詢寫入能力，`disabled` 亦未納入全站寫入能力。
- 影響：使用者可能花時間完整輸入與逐筆確認，直到保存或正式確認才得知環境不可用。這不能歸因於純 CSS，也不能用 Mock 通過宣告可上線。
- 修正：先確認目標資料來源與真實讀寫相依服務，再讓 UI 在開始作業前提供清楚的可用狀態。不要透過移除驗證門檻來讓畫面成功。

### F04｜P2：結構化 API 錯誤變成 `[object Object]`

- 規格：階段 32 的錯誤分類與可理解的復原提示。
- 實作：`lib/orders-v2-get.server.ts:112` 回傳 `error:{code,message}`，`components/useOrders.ts:8` 與 `components/OrderForm.tsx:21` 卻直接傳入 `Error(body.error)`。
- 本次無外部連線的重現：以實際 `useOrders.ts` 轉譯後注入結構化錯誤回應，收到的 `Error.message` 確為 `[object Object]`，而不是 API 提供的中文提示。
- 影響：無法向使用者說明權限、資料來源或查詢出錯原因；重試與人工排查缺少依據。
- 修正：統一處理字串／結構化錯誤，顯示 `message`，保留可診斷的錯誤分類。

### F05｜P1：問題摘要漏掉數量級距錯誤

- 規格：PDF 第 39、99、101–102 頁；數量規則應可理解、問題摘要能定位材料。
- 實作：`components/OrderMaterialLine.tsx:16` 只檢查最低量，未檢查級距；數量 input 為 `step="any"`。`components/OrderForm.tsx:63` 與 `:156` 用這份問題清單計數並決定能否前往最後確認。
- 例子：最低量 100、級距 100 時，150 是正數且不低於最低量，前端可未列入問題；後端仍會拒絕。
- 影響：先顯示沒有問題，正式提交才泛化拒絕，長清單難以找到哪筆需要改。
- 修正：共用精確數量驗證或取得可定位的伺服器預檢結果，讓問題摘要與正式驗證一致。不得另寫不一致的浮點餘數算法。

### F06｜P2：失焦提示未顯示；次要工具重複增加清單負擔

- `components/OrderForm.tsx:151` 在未開啟問題篩選或按下最後確認前傳入 `NO_ISSUES`，使 `OrderMaterialLine.tsx:31` 已設計的失焦驗證無法取得欄位原因。
- 每筆常態有合併勾選、更換、刪除、廠商及確認區，已保存材料另有原始資料入口。雖然使用連續清單，仍把多個次要決策反覆鋪在各筆材料下方。
- 修正：失焦後顯示該欄原因；將合併改為明確的選取模式，廠商與原資料按需檢視。仍需保留必要異常與正式驗證。
