# 單一 Sheets 清理與 UI 完成紀錄（2026-11-12）

已依使用者指定順序完成：固定資料契約 → 真實讀寫 → 清除舊庫相容與重複流程 → 依 GitHub 前版的白色工作面整理 UI。變更在本機工作目錄，尚未 commit、push 或部署。

## 程式清理

- 單一儲存契約為 Schema 3，沒有舊庫偵測、降級讀取、自動採用或雙寫。API contractVersion: 2 是目前傳輸契約，不是相容模式。
- 刪除 8 個停用的 Authority、Business Source、Classification、Grid Source、Line ID、Preflight、Read、Writer 模組；另移除已無使用者的 mutation guard 與 history wire。
- 刪除 PostgreSQL 套件、SQL 與佈建／舊環境測試工具。舊整合測試退出現行入口，保留所需 Origin／容量／Redis 斷言為獨立測試；不保留可被誤用的舊架構啟用命令。
- 寫入入口統一為 ordersExecutor；secureMutation 只處理授權、限流、鎖及稽核。刪除舊 Preflight／Writer 診斷分支、未使用的候選確認及歷程／寫入規劃。讀取統一至 single-sheet-queries.server.ts，移除舊全域 readiness／readonly 回應及前端分支。
- 保留現在仍使用的嚴格解析、永久材料 ID、內容指紋、精確數量、退回目標及確認簽章。舊版號樣式的純工具名稱不代表接受舊資料庫。
- 一次性離線搬移工具保留，避免丟失可稽核的來源轉換方法；業務路由不呼叫該工具。

## PDF 缺口與 UI 修正

資料庫欄位與合併永久 ID 採用使用者後續選定的固定資料契約，未恢復 PDF 中較早的舊庫欄位或合併 ID 規則。手機鍵盤與 Safari 真機仍屬未測範圍。

針對 [原需求審查](uiux-review-2026-11-11-requirements.md) A1–A5 完成修正：

|缺口|完成行為|
|---|---|
|文字叫料重複逐筆確認（PDF 43 頁）|在辨識清單核對後沿用 confirmed；自填項先明確選廠商。相關內容改動會取消確認，最後仍有整單唯讀確認。|
|一般修改後未回到原清單（25、85 頁）|桌機回清單並排詳情、手機回詳情；保留搜尋／原位置，顯示已確認更新。|
|級距檢查落到伺服器才出錯（39、99、101–102 頁）|前後端共用精確數量算法；最低量、級距、精度問題可在輸入失焦後看到，最後確認前攔截。|
|數量失焦沒有問題訊息（39 頁）|完整問題資料傳入材料列，以 touched／showIssues 決定呈現；篩選不改變整單驗證。|
|次要操作常態占據每一列（38–40、149 頁）|材料集中於白色工作區、細線分列；合併進入選取模式，搜尋與問題篩選收起；更換／刪除／首次保存資料整合到更多操作。|

同一組 8 筆長中文料名與備註，手機 390px 頁長由 6,866px 降到 4,501px（約減少 34%）；桌機由 5,584px 降到 3,680px。這是相同合成內容的瀏覽器量測，不是正式使用者耗時數據。

## 真實新庫讀寫驗證

使用現有程式服務帳號，明確標記為系統維護驗證，在新庫建立一張暫時草稿、把數量由 1 改為 2，再刪除。透過目前 secureMutation、ordersExecutor、單一 Sheets adapter 及真實 Redis 完成，不使用 PostgreSQL、不發通知。

- 三次業務 batch 都完成寫後讀回；同一材料永久 ID 在修改時保持不變。
- Redis PING、限流、擁有者鎖／核對／解除、持久稽核與 Audit_Logs 落盤皆通過；結束後沒有遺留寫入鎖。
- Orders、Draft_Item_State 在測試前後的原始型別資料逐格完全一致：原有 62 張需求、356 筆材料保留，3 張審核完畢需求的狀態不變。
- 測試草稿已刪除；Order_History 保留 3 筆維護事件及對應稽核，沒有清除真實寫入證據。舊庫未修改。
- 這是維護服務帳號驗證，沒有冒用真人登入身分；真人 OAuth 瀏覽器登入、正式通知收件與實際出貨操作未測。
